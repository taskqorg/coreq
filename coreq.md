# coreq contract
coreq is the shared Rust crate of taskqorg tools: install layout, self-update, launcher and rollback, OS service units, `status.json`, selftest harness, board token, profiling. This file holds every decision; README and code follow it. [taskq](https://github.com/taskqorg/taskq) is the reference consumer; its `taskq.md` § 4 and § 8 define the behavior extracted here.

## Rules
- **Shared rules.** [specq](https://github.com/taskqorg/specq) binds every task here, [spec first](https://github.com/taskqorg/specq/blob/main/engineering/spec-first.md) included; this file holds only coreq decisions.
- **No constants for a consumer.** Tool name, title, release repository, version and install folder are fields of `Tool`; a second consumer passes its own and needs no fork.
- **No behavior change on extraction.** With `Tool::new("taskq", "TaskQ", "taskqorg/taskq", VERSION)` every path, unit, message and check matches taskq.md § 8.
- **Dependencies.** `ring`, `serde_json`, `tracing`/`tracing-subscriber`, and bundled `rusqlite` for the shared durable local telemetry database and portable `flate2` for lossless bounded event blocks. No HTTP client: HTTP goes through the OS `curl`.
- **Checks.** `python3 scripts/check.py` selects the merge gate: documentation checks for prose-only changes, otherwise `cargo test --locked` for this shared crate. `--full` validates selection on workflow dispatch and before dependency-pin adoption; unknown impact uses the full suite. CI (`.github/workflows/tests.yml`) runs affected Rust checks on Linux, macOS and Windows; job `tests` is the required status. Elapsed budget:900s per GitHub-hosted `ubuntu-latest`, `macos-latest` or `windows-latest` runner, including toolchain setup, build and execution; the runner prints elapsed time and fails on exhaustion, without retries. A failed selector is repaired before reuse. Workflows grant `contents: read` only; a publishing job adds just what it writes. Vulnerability reports: SECURITY.md.

## Tool
`Tool { name, title, repo, version, install, fault }`. `name` names the binary (`<name>`, Windows `<name>.exe`), files and env vars; `ENV` below is `name` in upper case. `title` names the Windows Scheduled Task. `repo` is the GitHub `owner/name` of releases; it is built into the consumer binary, never read from project config: project files are written by agents, so config must not choose the code hosts run. `install` uses explicit env `<ENV>_INSTALL` first. Without it, an installed launcher or immutable release resolves its own installation from the exact executable location and the existing install layout; recognized launcher `.old` variants retain that root. A standalone/source executable uses `~/.local/share/<name>`, Windows `%LOCALAPPDATA%\<name>`. No cwd, home traversal, sibling or disk discovery. Resolve before capture/bootstrap and keep the resolved root for the process lifetime. A recognized but invalid or inaccessible installed layout is unknown/refused; never silently redirect it to another installation. Native service starts and their child entrypoints use this same rule; this changes no worker grant or filesystem permission.

## Install layout
- `install_dir(name, title, aliases)` resolves the process root before bootstrap; `Tool::new` uses it without aliases. A consumer names any existing auxiliary executable exactly, before its first resolution. Aliases do not grant permissions. Recognition uses only the executable's exact launcher/release/bundle layout, bounded current selection and the primary release file; no search. Explicit `Tool.install` values stay caller-owned. Launcher and update-smoke children receive the selected `<ENV>_INSTALL`, including first-install smoke before current exists.
- `releases/<ver>/<name>`: immutable release folders; `releases/<ver>.tmp/` is a download in progress.
- `current`, `previous`: one version each, written atomically (temp file, then rename).
- `releases/<ver>/starts/<project>`, `releases/<ver>/healthy`: launcher counters (below).
- `<name>`: the launcher, a copy of the binary that last updated or installed; `<name>.tmp` (Unix) and `<name>.old`, `<name>.old.<n>` (Windows) are leftovers of replacing it.
- `<name>.log`: host service output (Windows and launchd).
- `rollback-floor`: minimum launcher version, recorded by `launcher::set_rollback_floor` only after the consumer verifies host-unit ownership. An unreadable or invalid floor refuses service launch; an absent floor keeps legacy behavior.

## Acknowledged state files

`write_durable` accepts text or bytes and is for acknowledged files whose acknowledgment requires persisted replacement. The caller owns a lock covering the destination and its reserved `<filename>.pending` temporary file. Create the temporary exclusively, write and sync it, then replace the destination; Unix also syncs its directory, Windows uses write-through replacement. Only then return success. A failure after replacement is uncertain, never proof that the old value remains. An existing temporary file is preserved and refused for explicit recovery; this helper never guesses whether an interrupted write should become current. Errors remove only the temporary created by this call. Consumers retain their own corruption/schema checks and decide recovery without replaying business effects. `write_atomic` remains rename-only; it cannot establish an acknowledged power-loss durability boundary. Qualification uses process termination after acknowledgment, not simulated hardware power loss.

## Release
A `v*` tag builds `<name>-<ver>-<os>-<arch><exe suffix>` per OS (`os`: `macos`, `windows`, `linux`; `arch`: Rust's), `SHA256SUMS` and `latest.json` `{"version", "files": {"<os>-<arch>": "<file>"}}` under `https://github.com/<repo>/releases/latest/download/`. Trust is HTTPS to `repo` and who can push its tags; `ponytail:` no signature, add one when releases are served elsewhere. Release CI follows the [specq release contract](https://github.com/taskqorg/specq/blob/main/engineering/release-contract.md).

## Update (`update::update`)
1. Prune: delete leftover `releases/*.tmp` and, when `current` is set, every `releases/<ver>/` that is neither `current` nor `previous`, its exe first; one that fails (Windows: exe in use) is reported on stderr and kept for the next update. Read `latest.json`. Not newer than `current` (else `version`), or already present: no update.
2. Refuse a version with characters outside `[A-Za-z0-9.-]` or `..`, or a file other than `<name>-<ver>-<os>-<arch><exe suffix>`.
3. `check` stops here and reports the version.
4. Download the file and `SHA256SUMS` into `releases/<ver>.tmp/`; the file's sha256 must be listed with its name. Rename it to `<name>`, mode 0755.
5. Smoke: `<name> selftest` with `<ENV>_SELFTEST_OFFLINE=1`. Failure: delete the folder, report, keep current.
6. Rename to `releases/<ver>/`, write `previous` = old `current`, then `current` = `<ver>`. Replace the launcher with the new binary. Prune again, as in step 1. The consumer re-execs.

Versions compare by numeric dot parts; a `-pre` suffix sorts before its release (`4.1.0` > `4.0.12` > `4.0.0-dev`).
Replacing a binary on Unix, and the release binary of `install_self` everywhere: copy to `<target>.tmp-<pid>`, set the old file's mode, rename it over `<target>`; never write a binary in place (macOS kills a rewritten running binary); a failed copy deletes the temp file and leaves the old binary intact. Extended attributes (macOS quarantine) follow the source file, not the old one; Linux copies none. Replacing the launcher on Windows: renames the running `<name>` to `<name>.old`, or to the first `<name>.old.<n>` (n = 1, 2, ...) that is free or removable when an earlier one is still in use (a failed copy renames it back) and copies the new file. No live swap: a running launcher keeps its process until the service restarts.
`update::install_self`: copy the running binary to `releases/<version>/` and replace the launcher with it; make it `current` (old one `previous`) only when newer: never a downgrade.

Transactional consumers use `update::prepare_install(t, verified_bytes)` then `activate_install(t)`. The consumer serializes installation with its existing update/lifecycle locks, verifies/signs and freezes the exact bytes first and retains durable originals before activation. Preparation syncs an immutable release without changing launcher, current/previous or units; identical bytes reuse it, different bytes at the same version refuse and preserve it. Activation requires that regular prepared file, refuses unknown/current downgrade before effects, replaces the launcher from the prepared release and durably writes current/previous. A later activation error is uncertain, not a rollback: the consumer owns native observation and restart-safe restore. These primitives do not install/start a unit or prove health. The combined `install_self` remains an identified compatibility caller until consumers migrate.

## Launcher (`launcher::launch`)
- Runs `releases/$(current)/<name>` with the same arguments. No `current`: exit 1 with `run \`<name> update\``.
- Only `service run` counts starts of a version without `healthy`, per project: the counter is `releases/<ver>/starts/<project>`, `<project>` the name of the working directory (the project root). At a project's 3rd it writes `previous` into `current` and runs that only when it is not below `rollback-floor` (host mode below); starts of other projects do not count. `healthy` stays install-wide: the consumer writes it after `rollback_after`. A `starts` file of an older launcher is replaced.
- Unix: exec. Windows `service run`: the launcher supervises: frees its console, runs the child without a window, appends output to `<name>.log`; exit 75 restarts at once, any other exit after 60 s. Other Windows commands: run, exit with the child's code.
- Messages go to stderr as `<name>: <message>`.
- **Fault hook.** `Tool::fault` (default none) receives a `Fault` with `board`, `runtime`, `revision`, `contract` and `observed`/`inferred` empty; the consumer fills them and reports. Two points call it: the rollback above gives `update.rollback` (site `launcher:rollback`, fingerprint field and evidence `failed:<ver>`); on Windows a `service run` exit 101 gives `dispatch.panic` (site `launcher:exit`, evidence `exit:101`). No `previous` to restore: no fault. A hook that panics is caught: launcher behavior and exit code stay unchanged.

## Host service units (`service::host_unit`, `service::legacy_unit`)
`host_unit(t)` writes and loads one unit running `<install>/<name> service run` with `<install>` as its working directory and the caller's PATH. Names: launchd `com.<name>.service`, Scheduled Task `<title>`, systemd user `<name>.service`. launchd output goes to `<install>/<name>.log`; other settings match the legacy generators below. The consumer calls it only when installation or reload is safe; it does not drain children or migrate project configuration.

On Windows, explicit host installation registers management rights for the exact current-user SID and SYSTEM, including an elevated installer: `D:P(A;;GA;;;<current SID>)(A;;GA;;;SY)`. The principal stays InteractiveToken/LeastPrivilege and the logon trigger stays scoped to that user. Before updating an existing task, verify its principal, executable, arguments and physical installation directory by volume serial plus a 128-bit file ID; foreign scope refuses replacement. This accepts distinct canonical spellings of the same existing local path without prefix stripping or case folding. Read back the native management rights before starting or acknowledging installation. Runtime operations never repair existing task ACLs automatically; an unqualified existing task requires explicit installation repair. Worker/project grants do not change. Legacy project-unit generation remains compatible.

`legacy_unit(t, project)` unloads and deletes the legacy per-project unit and reads back unit absence from the native manager and filesystem. Unknown readback is an error, never success. The consumer must first verify that the legacy service and its children have exited; run removal from an idle helper when unloading would kill the caller. No other unit is removed. The legacy `unit` generator stays compatible.

For `service run` with `<install>` as working directory, unhealthy starts use `releases/<ver>/host-starts`, independent of project roots. The third start rolls back only if `previous` is at least `rollback-floor`; otherwise current stays. The floor setter accepts only valid versions, raises the floor atomically and never lowers it; it refuses a floor newer than current. The consumer serializes floor recording with topology installation. Recording the floor is separate from unit loading: only the consumer can verify host ownership. Legacy per-project starts keep their existing counters and also honor the floor.

## Legacy service units (`service::unit`)
One unit keeps `<install>/<name> service run` running in the project root with the caller's `PATH`, restarting on failure.

| OS | Unit | Load | Unload | Stop (unit retained) |
|---|---|---|---|---|
| macOS | `~/Library/LaunchAgents/com.<name>.<project>.plist`, `KeepAlive`, output `<install>/<project>.log` | `launchctl bootstrap gui/<uid>` | `launchctl bootout gui/<uid>/<label>` | same as unload |
| Windows | Scheduled Task `<title>-<project>` from `<install>/<title>-<project>.xml` (UTF-16 with BOM): this user's logon (`whoami`), no admin, no time limit, restart every minute | `schtasks /Create /XML /F`, `/Run` | `/End`, `/Delete /F` | `/End` |
| Linux | `~/.config/systemd/user/<name>-<project>.service`, `Restart=always`, journal | `daemon-reload`, `enable --now` | `disable --now` | `stop` |

Stop retains the autostart definition. launchd and Task Scheduler keep their logon trigger; systemd user units start with the user manager or an explicit native start. With linger, a new login does not restart that manager. Consumers state the actual restart condition instead of promising every login restarts a stopped service. No login watcher is added.

`schtasks /End` ends only the launcher: the consumer also ends the service process tree. Commands run with captured output and no console window.

## status.json (`status`)
Each service pass writes `<root>/.<name>/status.json` atomically. Common keys: `host`, `version`, `pid`, `at` (unix seconds), `project`, `error` (null when the pass succeeded), `update` (a newer version found and not installed, else null). Consumers add their own keys. A reader treats a file older than its freshness limit (taskq: 60 s) or unreadable as unknown, never as zero or success.
Publication runs through the shared execution boundary: a failed directory/write/rename records `status-write` even when a caller handles it. The original error returns to the caller; paths and status contents never enter capture. A successful write proves publication only, not service health or command application. Consumers report failed publication without abandoning owned children and cannot qualify health from an unpublished pass.

## Selftest harness
The consumer's `selftest` command loads config, runs its built-in fixtures and, unless `<ENV>_SELFTEST_OFFLINE` is set, reads the board. It writes nothing. Update smoke (step 5) and release CI run it on each artifact; a version whose selftest fails is not published or installed.

## Incident reports (`incident`)
Implements the [taskq incidents design](https://github.com/taskqorg/taskq/blob/main/docs/design/incidents.md) for any tool. The consumer owns its fault catalog: it detects a fault at a fixed point (the launcher detects `update.rollback` and Windows `dispatch.panic` for it through `Tool::fault`, § Launcher) and passes a `Fault` (code, fingerprint fields, board, runtime, site, revision, contract, evidence, observed, inferred). coreq builds, checks, routes and stores the report; it never prints, panics out, exits or touches consumer state.

- **Switch.** Env `<ENV>_INCIDENT_REPORTS=off` or config `false`: `disabled`, nothing written or run. Config absent (an existing project before the owner chose): `local`, reason `not acknowledged`. Only `true` sends. `incident::disclosure` is the text setup and the first update show before any send: destination (the public `repo`), posting account, payload keys, fallback, opt-out.
- **Report.** Schema `<name>-incident/1`, one JSON object of at most 4 KiB with keys only `schema`, `fault`, `fingerprint`, `report_id` (random UUID), `release`, `revision`, `contract`, `board`, `runtime`, `os` (`<os>-<arch>`), `site`, `evidence` (at most 8), `observed`, `inferred`, `profile` (`profile::window`, § Profiling). Values are codes of `[A-Za-z0-9._:/-]`, at most 64 characters, no leading `/` or `//`: no free text, link or mention. `fingerprint` = first 16 hex of sha256 over the schema major, fault, its fingerprint fields, board, runtime and os; never the release. Any other key, value or size: `local`, reason `unsafe`, no file.
- **Login.** Only a github.com token: the board token when the board is github.com, else the `gh` login for github.com. None: `unsupported-auth`. HTTP goes to `api.github.com` through `curl`; the token goes on stdin, never in arguments.
- **Route.** Search the `repo` issues whose title holds the fingerprint: at most 2 pages of 100 and 5 s, then the exact marker `<!-- <schema> <fingerprint> -->` in the body; incomplete, failed or over budget: `local`, reason `search incomplete`. Open match: one `confirmed` comment unless this account already confirmed this release (at most 2 comment pages). Closed match: this release seen: no write; newer release: one `regression` comment; never reopen. No match: create the issue `<name> incident <fault> <fingerprint>` with label `incident`. At most one write per report; a failed write is looked up by `report_id` read-only, else `local`, reason `unknown delivery`. One report per fingerprint per process; no retry store.
- **Claim.** Before the search a report claims the fingerprint with an atomic create of `<install>/incidents/<fingerprint>`, writes the issue link into it once known and removes it when delivery fails. A sibling that finds the claim never creates an issue: with a link it routes as above but takes the link when the search misses the issue; without a link it skips, `local`, reason `claimed`, unless the claim is older than 10 minutes, then it reclaims.
- **Outcome.** `sent` (link), `local` or `unsupported-auth` (reason, `<root>/.<name>/incidents/<fingerprint>.json` with the sanitized JSON for manual submission), `disabled`. `Outcome::json` is the `status.json` `incident` value `{state, fault, at, path, url, reason}`. A report never reports itself: a nested or panicking report ends `local` without a write. The first report installs a panic hook that stays silent while a report runs and otherwise delegates to the previous hook, so a caught panic prints nothing; a hook the consumer sets later replaces it.

## Board token (`token`)
Env `<ENV>_TOKEN`, else `GITHUB_TOKEN`/`GITLAB_TOKEN`, else `<install>/token` (0600), else `gh auth token --hostname <host>` / `glab config get token --host <host>`: only the board host's login. Never in config, never sent anywhere but the board API.

## Profiling (`profile`)
The aggregate profile below is the compatibility view. New universal observations use `telemetry`; consumers migrate without deleting retained legacy observations.

## Universal telemetry (`telemetry`)

- Quiesced maintenance: `telemetry::maintenance(path)` returns the existing writer-election guard, refusing a live broker. The caller holds it before opening its one owner Store, through completion/drop; it never stops another writer. `Reader::import_cursor` reads committed source progress without writer authority.
- JS architecture (accepted target2026-10-17): ordinary module methods inherit counters and bounded selected diagnostics from one shared module wrapper; events, commands, rendering and owned asynchronous work enter explicit shared execution boundaries. Runtime code is not rewritten by a build-time JS parser. Wrapped logic/view methods are synchronous and preserve receiver/arguments/return and thrown identity. Async effects have one owner, keep their initiating context, observe settlement and deliver results through a wrapped synchronous callback; callback exceptions are recorded and forwarded through the platform reportError hook when available; components do not own detached promises. `observe_linked` preserves externally supplied identities and unlinked aggregates rather than inheriting the receiver; external diagnostic methods share the native quota/expiry. The Rust `capture::bind` adapter carries a dispatcher/link into an owned thread callback. Context-bound synchronous JS callbacks retain the initiating scope across owned timer/Promise handoff. Diagnostic selection emits its bounded metadata through the same transport. Promise settlement is distinct from submission, frames from paint. The same source is exported by the Rust constant and the pinned `@taskq/coreq` JS package. `shared()` reuses one realm-owned runtime across components and coalesces dirty method counters into one2s flush timer, including calls without DOM events; an idle runtime has no recurring timer. Health metadata uses this same flush; `connect()` supplies the existing synchronous transport, with absent delivery explicitly lost. The consumer transports bounded metadata into the existing capture writer; no second collector/store. The selected gate uses the runner’s Node.js through the existing bounded executor for JS wrapper conformance. Full consumer module/boundary inventory, new-handler inheritance, errors, privacy and native/load checks remain required before claiming coverage.
- Analysis: `telemetry::Reader` opens an existing schema6 store read-only. Inside its snapshot `open` runs only cheap checks: schema and application id, non-negative retention metadata, and the sequence high-water mark against the retained maximum and pruned floor; it never scans the store, so an open reader does not hold the snapshot for a full validation. Each page decodes and validates the rows it reads and reports a corrupt row as an explicit error. The full scan (SQLite `quick_check`, retained bytes, orphan blocks, every row) runs only in the owner `Store` open and maintenance, never in writer promotion or in an open of a sealed, unchanged store (see Local writer transport). Its bounded export pages share the store decoder and retention metadata and read one committed SQLite snapshot until the reader is dropped. It never creates a missing store, upgrades, takes a writer lock, checkpoints or prunes. Missing, foreign, older/newer or corrupt stores are explicit errors. SQLite may use WAL shared-memory sidecars; callers must release the snapshot before slow external output, and existing storage limits still bound writers while a snapshot is pinned. This API requires existing file-read permission and grants no access by itself.

- One shared implementation for all consumers, local first and always available without a connection. Consumer execution adapters supply identities and observations; no product forks the storage or synchronization bookkeeping. The target coverage is the complete [shared contract](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md#coverage-by-construction), including native/WebView input, windows, resizing, rendering, commands, agents, tools and context/compression. A storage API alone does not qualify that coverage.
- Store: a consumer-selected stable path below its installation, SQLite WAL, `synchronous=FULL`, a prepared writer with a 1 s busy timeout. Initialization is serialized by `<database>.init.lock` with a 1 s deadline. Every store mutation and initialization takes the owned OS lock `<database>.write.lock` before SQLite; it queues cooperating connections/processes outside SQLite rather than starving another writer at `BEGIN IMMEDIATE`. External SQLite contention still obeys the 1 s busy timeout; async qualification flush keeps its 3 s deadline. One writer connection per `Store`, shared by callers; the process reuses that store. Group writes commit in one transaction and return ids only after commit. Unacknowledged writes may be lost on crash; acknowledged writes survive process restart. Corrupt or newer-schema stores are preserved and refused, never reset. SQL schema version is 6. Schema5 upgrades atomically by backfilling a validated kind column and its kind/sequence index; payloads are not rewritten. Schema4 upgrades without payload rewriting; schema5 is the reader floor for partitioned count summaries. Schema3 upgrades without payload rewrites; the new reader floor admits semantic metadata and explicitly unknown historical identities. Schema2 upgrades transactionally without rewriting existing compressed payloads; older readers must refuse the new version. A completely empty, unowned schema-0 file is initialized in place after an interrupted bootstrap; schema-0 files with any object or application id are refused. Schema-1 upgrade is one FULL transaction: validate the original observations, repack rows with block/slot references in the same table, temporarily muting only this connection's triggers so retention counters and user callbacks do not observe deletion and preserve ids, sequences, source/receipt times, retention metadata, sync/import cursors and the events AUTOINCREMENT high-water mark. Pre-commit failure rolls back schema and rows; a post-commit checkpoint error preserves the committed schema-6 data and refuses this open. Unknown schemas remain refused.
- Shared physical budget: `telemetry::Budget` names an existing installation lock, explicit peer files, a total byte ceiling and reserved text/metadata space. `Store::open_bounded` and `Runtime::install_bounded` reuse the normal store/writer. Every initialization and mutation holds that lock and measures peer file lengths. The budget fixes the shares (owner decision 2026-10-19): `total/2` is the working share and the other half is a reserve that steady retention never uses. Inside the working share, `reserved` holds legacy text, IPC metadata and peer stores; the rest splits 6:1 into the database cap (at most 384 MiB) and the WAL+SHM share. Consumers pass `telemetry::INSTALLATION_BYTES` (1 GiB) and `telemetry::PEER_BYTES` (64 MiB): database 384 MiB, WAL+SHM 64 MiB, peers 64 MiB, reserve 512 MiB. Peer growth never shrinks the database cap. A share over its limit (`peer-share`, `database-over-cap`, `wal-over-share`, `reserve-used`) or a capacity prune by this store (`capacity-pruned`, kept for the store's lifetime) is a degraded diagnostic in `storage()` plus one stderr line per process, never an error to callers. Missing peers count as zero; inaccessible, non-file or symlink peers refuse. A bounded store over its cap (a smaller budget, or one over the old 64 MiB budget) opens, prunes oldest whole observations to 60% of the cap and stays `degraded` until `reclaim` shrinks the file; no manual deletion. A changed cap checkpoints before reconfiguration. Bounded connections disable SQLite's implicit last-close checkpoint; explicit checkpoints run under the budget lock and committed WAL survives close/reopen. Peer writers must use the same lock and calculation; arbitrary external file writers are outside this contract. The lock has a1s admission deadline. The capture writer retries a batch that failed on contention (`budget-locked`, `sqlite-busy`, `transport-unavailable`) with the same event ids every 50 ms for up to 10 s; the bounded queue absorbs new arrivals meanwhile, and only a batch still failing after that window or any other failure counts as lost. IPC binds the budget descriptor: a bounded client refuses a writer with a different or absent budget. Unbounded consumer APIs retain their existing limits.
- Compact payloads: Portable zlib-rs level1 blocks hold up to1024 complete JSON payloads and1MiB decoded framing. The frame carries a version, count, decoded size and checksum-protected stream; decoding rejects unsupported, oversized, truncated, corrupt, non-UTF8 or trailing data. Events retain indexed identity/time fields and reference a block/slot; pruning the last reference releases the block. Eight decoded blocks at most are cached per read operation. Exported observations, order and receipts are unchanged. Already open schema-1 writers may still insert raw payloads; schema-6 readers validate/read these rows too. Old readers cannot interpret compressed rows and must not be used after cutover. A later open atomically compresses remaining raw rows from an older writer too. No source store or historical row is silently discarded. Capacity reservation covers incoming payload bytes plus512bytes per new indexed row and32pages of block/index slack; SQLite's physical cap and transactional rollback remain authoritative.
- Observation: immutable random id (historical import derives it from a stable namespace and position); product/version, operation/kind, trace/span/parent identities, source UTC start and monotonic duration, outcome/error codes; optional project/host/runtime/task/attempt and model, context/token/compression measurements. Fixed codes and finite numbers only; no task text, arguments, prompts, output, keys or paths. Unknown values are null with an explicit reason.
- Bounds: newest observations within 30 days and the physical database cap, whichever is smaller. The same writer prunes oldest whole observations transactionally; a single observation is at most 16 KiB. Database pages are reused; WAL checkpoints run after pruning. Unbounded `Store::open` keeps its 28 MiB database cap, 29 MiB WAL cap and 1 MiB SHM allowance; bounded stores use the budget shares above. SQLite pages must be at least 1024 bytes. Each cooperating mutation holds the shared writer lock and disables cache spill/automatic checkpointing. Append first reads SQLite NOOP checkpoint frame counts: it skips RESTART only when the current frames plus a worst-case transaction, 24-byte frame headers, WAL header and up to one 64 KiB sector of repeated commit frames fit the WAL cap. The worst case is a full database for unbounded stores and one maximum append group (16 MiB payload, 512 bytes per row, 32 pages) for bounded stores. Otherwise it checkpoints with RESTART before beginning; a bounded WAL already over its share truncates instead, and an append that leaves WAL+SHM over the share truncates after its commit (a busy truncate leaves it degraded, never fails the committed append). An unbounded append's checkpoint waits for readers up to the busy timeout. A bounded append's checkpoint never waits for a reader (taskq#1517): one that a pinned reader leaves unfinished is counted in `storage()` `unfinished_checkpoints` and retried by the first append after 1 s, and meanwhile appends commit into the reserve while peers, database, WAL, SHM and one maximum append group fit the installation total; past that total the append refuses as `sqlite-busy`. Other mutations retain that checkpoint and open/explicit prune truncate. Checkpoint, migration, import, rebuild and large capacity prunes may exceed the WAL share transiently inside the reserve; the database cap bounds that transaction. The maximum transaction includes sector padding rounded up to a complete frame. This reuses bounded allocation without forcing database synchronization for every small append. A pinned reader may coexist with appends inside that allowance; when a checkpoint is required, a pinned reader refuses an unbounded append and every other mutation without advancing data or cursors. Capacity pruning and the new batch commit atomically. When used pages plus the batch reach 80% of the cap, oldest whole observations are removed until 60% remain; `poll` aggregates and `poll.change` records go last. Larger preexisting unbounded databases are refused and preserved, never reset. storage() reports file allocation, limits, retained payload and pruning. Export states retained sequence/time bounds and pruned count; pruning is not evidence that an operation never occurred.
- Agent analysis reads committed rows through the shared JSON export, without board or network access. Indexed sequence and source time support bounded windows/batches. Source `started_ms` may be null only with an explicit unknown reason. The SQL source-time index reserves -1 for unknown (never a reported timestamp); canonical observations retain null, and known source timestamps remain nonnegative. Time-filtered exports include unknown-time observations conservatively and expose `unknown_started_count` for the retained history; known time bounds exclude the reserved key. Receipt time remains independently required and drives expiry. Schema6 is the reader compatibility floor for indexed semantic observations. Historical version/trace/span can be null only with explicit reasons; adapters never invent a product version or trace. Semantic fields retain `open`, `from`, `to`, `source`, `usage_status`, numeric `run_id`/`process_id`/`span_id`/`parent_id`, `entry`, `previous_seconds`, `remaining`, `calls` and `tokens`. `counts` is a bounded-by-event-size object of fixed code keys and unsigned counts. Numeric metadata preserves u64; source timestamps alone must fit signed SQLite milliseconds. Schema, frame size (17 MiB), batch count (up to 8192), decoded payload (16 MiB), ids, endpoint and acknowledgment are validated. An older or raw store still takes the full owner open. - Store spans: always-on spans `<product>.operation.telemetry.election`, `telemetry.open` and `telemetry.checkpoint` date writer election, owner open with its full scan, and each checkpoint. `from` names the trigger: election `bootstrap` or `promotion`; open `first-open`, `schema`, `promotion`, `orderly-exit` or `unclean-exit`; checkpoint `open`, `upgrade`, `capacity`, `seal`, `budget`, `wal-room`, `wal-share`, `import`, `acknowledge`, `prune` or `reclaim`. `to` names the outcome: `owner`/`client`, `scan`/`skip`, `complete`/`busy` with `remaining` frames. The span duration is the wait. `Runtime::install` opens its store under the new collector, whose writer waits for that store, so the bootstrap election and open are kept; `qualify` requires committed observations beyond these bootstrap spans, and an existing global subscriber is refused before the store is opened. Spans need an active collector; a checkpoint span emitted by an append is committed by a later append, and a bounded append retries a busy checkpoint at most once a second, so a pinned reader cannot start a span feedback loop.
- Polling: `capture::poll(name, subject, action, state)` runs `action` on every call and returns its result unchanged; `state` names the observed result with a fixed code. `process::identity` uses it (`present`, `missing`, `denied`, `process-identity`), as does `status::write` (`written`, `status-write`); consumers wrap their own repeated status checks the same way and report `changed` themselves. `subject` (`u64`: the PID, a hash of the status root) separates fold keys and is never stored. - Required receipts: `Capture::commit` submits one immutable event through the existing bounded writer and acknowledges only that event's FULL commit. ## Bounded command execution

`process::identity(pid)` reads a PID plus its native creation identity: Linux boot ID/start ticks, macOS creation seconds/microseconds, Windows process creation FILETIME. Missing PID returns None. On Windows, a signaled process handle also returns None even while another handle keeps the exited process object accessible; zero-time native wait errors remain unknown. Invalid PID, denied access, an existing process whose creation identity is unavailable (including hidden/zombie cases), malformed native data and unsupported OS return an error. This read grants no ownership or termination permission. Equality identifies one native process, not its descendants or external effects. Consumers persist only identities needed for their existing recovery records and must use owned handles/native exit evidence for control. Telemetry records the operation/outcome, never raw identity values. TaskQ is the first consumer; existing command APIs remain unchanged. Target OS qualification is required before relying on the read for recovery.

`process::terminate(&Identity)` requests termination only through a native mechanism that binds the signal to the verified process incarnation. The caller must already have authority over that recorded execution; identity lookup does not grant it. Success confirms the request, never exit or descendant termination. macOS reads the native PID version, verifies the saved creation identity, and uses the kernel audit-token signal check. Linux opens a pidfd before checking the saved boot/start identity, signals through that descriptor, and closes it on every outcome. Windows opens a handle with query, synchronization and termination rights, compares the saved creation FILETIME and live state through that same handle, then calls TerminateProcess on it; PID reuse cannot retarget the request. Denied, missing, changed or unsupported native capabilities return an error without a PID-only fallback. Other targets currently return unsupported. Consumers must still read native exit before releasing capacity. Operation telemetry excludes identity and token payloads. Target-platform checks qualify each mechanism separately.

`process::output` owns a direct subprocess, null stdin and both captured output pipes. Callers pass a fixed operation code and a positive deadline up to1h; stdout+stderr payload is at most1MiB. At most16 executions, including unfinished cleanup, own capacity at once. No command, arguments, environment or output enters telemetry. The caller retains the real output/OS error. `process::exchange` uses the same owner for bounded stdin bytes (at most1MiB) and a combined response of at most8MiB. Input never enters argv, temporary files or telemetry.

- The shared execution boundary records spawn, exit, wait/read/write error, timeout, input/output limit or capacity failure before a caller handles the result. A nonzero exit returns its Output with the failure. Success requires complete input, child exit and both pipe EOFs before the deadline; a descendant holding a pipe makes completion unknown/timeout.
- Nonblocking pipe reads use no detached reader threads. A stdin exchange has at most one owned writer thread, sharing the execution deadline and capacity. Cleanup retains its handle and permit until the child is reaped and the writer finishes; inherited stdin may retain capacity but cannot block the caller or create unbounded threads. On error or unwind, terminate the owned direct child. A single bounded reaper owns unfinished cleanup and its observation until try_wait confirms exit and input completion; do not block the caller on wait or lose the child handle. Unreaped children retain capacity and unknown cleanup status. Unexpected cleanup-owner failure reports failure and retains its child handle/capacity until process exit. Kernel spawn/I/O calls and OS scheduling are not hard real-time guarantees.
- HTTP exchange adapters preserve credentials on stdin and their HTTP parsing/error rules. Enrollment uses15s around curl's10s; incidents use their existing remaining deadline plus5s. Protocol success requires a successful process and a complete response; timeout or failed input never makes a partial response successful.
- Shared adapters use30s for native service commands/readback/identity, Windows storage identity/ACL helpers and update candidate selftest; downloads use305s around curl's existing300s limit. A timed-out selftest never promotes a candidate. Ignored native nonzero exits retain their captured failure; spawn/read/timeout failures are never ignored.
- CLI credential lookup uses10s and the same bounded executor. A failed lookup is unavailable, not evidence that no credential exists; the legacy token counter uses `unknown`, while the executor retains the specific failure. Captured output remains private to the token adapter.
- Windows storage protection keeps the same owner ACL and refuses failed identity, empty identity, nonzero exit, timeout and output overflow. Collector bootstrap/maintenance disables tracing around its own native helpers to avoid recursive collection; connection callers retain helper failures.
- This helper does not own arbitrary descendants or replace long-lived worker supervision. It does not widen permissions, change process groups, retry commands or turn a successful spawn into completion. Consumers own per-operation deadlines and domain-specific interpretation of exit status.

## Legacy profiling (`profile`)
Follows [specq profiling](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md). coreq measures its own calls below; a consumer records its operations with the same `profile::record` and passes their budgets to `profile::report`.

The adapters below use one internal measured boundary: the existing capture operation records their logical result and fixed error class before the caller handles it, while the legacy memory counters retain the same measurements. Native subprocess observations remain child operations; a successful process is not a successful credential or HTTP result. No token, URL, response or error text enters capture. `record`, `flush`, `report` and `window` remain compatibility APIs with their existing formats; capture does not automatically flush or create `profile.json`. Consumers using the shared store need no compatibility-file writer.

| Operation | Call | p95 budget | Error budget |
|---|---|---|---|
| `forge.read` | GitHub API `GET` (incident login, search, comments) | 2 s | 5% |
| `forge.write` | GitHub API `POST` (incident issue, comment) | 5 s | 5% |
| `release.read` | `update::download` (`latest.json`, `SHA256SUMS`, binary) | 60 s | 5% |
| `token.read` | `Tool::token` and the `gh` login of `incident::github_token` | 1 s | 1% |

- **Counters.** Always on, in process memory: per operation count, outcomes `ok`, `failed`, `cancelled`, `retried`, max and the last 64 durations (p50, p95), error classes. Classes: `rate_limit` (HTTP 429, or 403 naming a rate limit), `auth` (401, other 403), `http`, `timeout` (curl exit 28), `network`, `json`, `spawn`, `missing` (no token). coreq never retries; a consumer that succeeds only after a retry records `retried`, not `ok`.
- **Store.** `profile::flush` merges memory into `<root>/.<name>/profile.json` atomically; the consumer calls it once per service pass. Bounds: 32 operations (least recently seen pruned), 64 durations and 8 classes (the rest `other`, also for a stored record) per operation, 256 trace spans. Names and classes are codes of `[a-z0-9._-]`, at most 32 characters: an operation with another name is dropped, another class becomes `other`. No secrets, content or paths. A failed write keeps the measurements in memory for the next flush. An unreadable store is replaced; a corrupt operation record (zero count, outcome sum that disagrees or overflows, a sample above `max` or more samples than calls) is dropped on flush; counters saturate, never wrap.
- **Traces.** Env `<ENV>_PROFILE=trace` at flush writes the spans `{op, ms, outcome, class, at}` recorded since the last flush; otherwise the store holds none. The store's `trace` key reports the switch.
- **Report.** `profile::report` lists every budgeted or stored operation: count, window (`since`, `at`), p50, p95, max, failure and retried rates, spread (p95/p50), classes, budget and state `ok`, `over` or `unbudgeted`. `slow` ranks measured operations by p95 over their budget (unbudgeted after, by p95), `failing` by failure rate, `unstable` by retried rate, then spread. Budget states and ranks compare unrounded values; the report rounds rates to 3 places and spread to 2 for display only. An operation without samples reads `unknown`, reason `no samples`; a corrupt record `unknown`, reason `corrupt`; never zero. No store: state `unknown`, reason `no samples`; unreadable store: `unknown`, reason `corrupt store`.
- **Incident link.** Every incident report carries `profile`, from `profile::window` over the store as of the last flush: `window:<since>-<at>` (else `window:unknown:<reason>`), then at most 7 operations over coreq's budgets as `<op>:over`, slowest first. The issue body's JSON and each `confirmed` or `regression` comment (line `profile <codes>`) carry it. Codes only, so the report's 4 KiB and code checks hold.

## Advisory file locks (`file_lock`)

`try_lock(path)` opens an owned lock file and returns a nonblocking exclusive guard or the native lock/open error. The guard explicitly unlocks before closing its descriptor: an inherited child descriptor must not keep the parent operation locked after guard retirement. Initialization and update callers keep their existing paths and wait policies; this API neither unlinks lock files nor changes ownership. `try_lock_file` and `try_lock_shared_file` take an already opened file; `Lock::file` borrows that same protected handle for bounded I/O. Release errors are reported, not silently discarded.
